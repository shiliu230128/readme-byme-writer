# Core：素材地图 · 事实层模板 · 质量算子

本文件每次都加载。三部分：怎么捞素材（不让用户去找 case）、事实层长什么样、判定质量的算子。

---

# 一、事实层：摄取与结构

事实层把"产品是什么"与"怎么说"分离。同一份事实可渲染成 README、售卖页、落地页、投放文案。

## 核心原则：不让用户创造素材，只让他指路

写文案的人手上通常没有用户的真实生活细节，这是**素材缺口，不是表达缺口**。解决办法不是让用户"去找几个 case"，而是去素材已经存在的地方捞。

### 素材地图（按优先级自动读取）

**README 侧**

| 需要的信息 | 去哪里读 |
|---|---|
| 真实用法示例 | 测试文件（最好的示例来源）、`examples/`、demo 脚本 |
| 环境前置条件 | CI 配置（`.github/workflows/`）、Dockerfile、`package.json` engines、`pyproject.toml`、`.nvmrc`、`requirements.txt` |
| 依赖与版本约束 | 锁文件、manifest |
| 现成 FAQ 与报错 | issue 列表、客服/群聊记录、`CHANGELOG` 的 fix 条目、**代码里的错误信息字符串**（每一条 throw/raise 都是一个读者会看到的报错） |
| 配置项全表 | `.env.example`、config schema、命令行参数解析代码 |
| 入口与启动方式 | `package.json` scripts、`Makefile`、`main`/`__main__`、导出声明 |
| 可视化物料 | 现有截图、`docs/` 图片、demo 视频、社交媒体已发的图 |
| 许可证与维护信号 | LICENSE、commit 频率、tag 历史 |

**售卖页侧**

| 需要的信息 | 去哪里读 |
|---|---|
| 痛点原话 | 客服记录、售前咨询、退货原因、已有评价、社群提问 |
| 新品无自有素材时 | **竞品评论区的差评**，最浓缩的痛点库 |
| 硬参数 | 参数表、详情图、说明书、供应商资料 |
| 反对意见（写 FAQ 用） | 售前咨询里被问最多的三个问题 |
| 价值锚点 | 替代方案的成本（人工时间、竞品价、自己 DIY、什么都不做的持续损失） |

材料里读不出来的通常只有两件事：**给谁用**、**和什么比**。这两件才值得占用提问额度。

# 二、通用质量算子 C1–C8

这些算子跨两类文案通用。它们是**反面规则**而非正面范例：反面规则数量少、跨品类稳定、复用率高；正向案例库需要按品类无限堆积，永远不够。

## C1 · 反证测试（一条规则覆盖多个难点）

把句子里的产品名/主语替换成**任意同类竞品**，句子是否仍然成立？

- 仍成立 → 这句话零信息量，重写
- 不成立 → 通过

适用位置：定位句、痛点句、卖点句、差异化条目、第一屏人群认领。

- ❌「基于先进架构的高性能数据处理框架」→ 换成任何库都成立
- ✅「让你不用手写分页逻辑，就能给已有接口加上游标分页」→ 换成别的不成立

## C2 · 具体度闸门（含反编造条款）

任何承担说服职责的句子，必须至少含一个可核验元素：数字 / 时间 / 地点 / 具体动作 / 型号 / 用户原话。

- 一段里连续出现 3 个及以上纯形容短语且无可核验元素 → 判定为模板腔，重写
- 痛点句必须含时间或动作细节（「洗完澡伸手拿毛巾，发现钩子在门后够不到」而非「收纳不方便」）

**但具体度只能来自素材。** 这条要求会诱发一种失败：为了"具体"而编细节。编出来的细节比抽象表述更糟，抽象只是无效，编造是当场暴露作者没有真实素材。素材不够时，把句子退到素材支持的抽象层级，不要补虚构细节。

- ❌「想要一份自己的观影记录，但用 Excel 记了三次就放弃的人」：Excel 和"三次"都是凭空填的
- ✅「想留一份自己的观影记录，但手动记表格总是记几次就断了」：保留了行为，去掉了假精确


## C3 · 证据转译三段式

`客观事实 → 可测结果 → 用户感受`，中间一环不可省。

- ✅ `1200W → 500ml 90 秒烧开 → 早上不用提前 5 分钟起`
- ❌ `1200W 大功率，吹得又快又干`（用参数直接证明体验，缺转译）
- ❌ `做工精良，品质卓越`（用形容词证明形容词）

无证据的卖点：降级为辅助描述，或删除。**不允许留在主卖点位。**

## C4 · 缺口协议（缺口不进正文）

质量最大的敌人不是写得差，是用模板腔把所有空白填满，看起来完整，实则空洞。但把 `[待确认]` 塞进正文也是错的：正文是给读者看的成品，读者不关心作者缺什么素材。

**规则：正文里不出现 `[待确认]`。** 处理方式按缺口类型分：

| 缺口类型 | 正文怎么办 | 例 |
|---|---|---|
| 缺了读者也不会卡住 | 整段不写 | 缺 star 数 → 不提数量 |
| 缺了读者一定卡住 | 写成读者能自己解决的通用做法 | 不知道客户端 skill 目录 → 写"在客户端设置页或文档里搜 skill / 扩展 / 插件" |
| 缺的是承诺类信息 | 不写，等用户补 | 价格、联系方式、许可证 |

缺口清单**只出现在回复里**，格式：`缺什么 | 补了能修好什么`。

例：`实测烧水时间 | 补上后可把"烧水快"从辅助描述升级为主卖点`

## C4b · 可懂度复述测试

C2 管"有没有信息"，这条管"读者能不能解码"。任何承担说服职责的句子，问：**一个不熟悉这个产品的人读完，能不能复述出发生了什么？**

- ❌「每周想看点什么，但每次挑片都花掉二十分钟，最后还是划走的人」："划走"是谁在划、划的是什么，读者要自己拼
- ✅「每周都想看点什么，但一打开视频软件就在片单里翻，翻了二十分钟最后关掉去刷手机」

同理，任何解释产品机制的句子必须自带上下文，**先说机制，再说好处**。省掉机制只留好处，读者会卡在半句话上：

- ❌「它会把"这片子好不好"和"我当时看得下去吗"分成两个分数记——加班那天看不下去的好片，不会被算成你不喜欢这类」：机制被压进破折号，读者不知道这两个分数是什么时候、由谁填的
- ✅「记录看完时它会问两个分数：这片子本身好不好，以及你当时看得下去吗。分开记是因为加班那天看不进去的好片，不该被算成你不喜欢这一类」


## C5 · 禁用词表

**两类都禁**（除非量化证据出现在同一句内）：
高性能、现代化、优雅、轻量级、强大、极致、领先、颠覆、赋能、闭环、深度融合、全方位、一站式、无缝、完美、海量、超强、智能化

**README 额外禁**：促销腔、催促语、无量化最高级、"仅需一秒"类夸张、竞品贬损

**售卖页额外禁**：绝对化违规词（最、第一、国家级、100%、永久）、医疗功效暗示、伪造数量词

## C5b · 非技术读者可读性闸门（README 专用）

面向零基础读者时，逐条检查：
- 出现的每个技术名词，首次出现处有没有一句白话解释？（用本文件表 4 核对）
- 有没有把"工程语言的优势"当卖点？（"更现代的架构"对非技术读者是零信息，必须转译成"你不用再做什么"）
- 有没有把命令行当成默认路径而没给图形界面/zip 替代？
- 每个代码块上方有没有一句"这行是干什么的"？裸命令对零基础读者是恐吓。
- 有没有把只对维护者有意义的信号当卖点？（测试通过数、代码行数、覆盖率，非技术读者无法评估，属于噪音）

## C5c · 依赖边界核对（防止说反话）

产品的依赖分三层，混在一起就会写出自相矛盾的句子：

| 层 | 例 |
|---|---|
| 产品自身 | 这个项目的代码要不要联网、要不要密钥 |
| 让它跑起来的宿主 | AI 客户端、浏览器、运行时。它们的联网和账号需求不由你决定 |
| 读者已有的东西 | 已经装好的客户端、已经有的账号 |

两条规则：

**一、凡写"不需要 X"，必须限定到层。** 跨层断言即为错误陈述。

**二、宿主是产品核心功能的必要条件时，不许把宿主的需求说成"不需要"。** 判据：这个能力是谁提供的？靠宿主提供的，宿主的依赖就是读者的真实成本，不能藏。

**三、归清层之后只讲一次。** 前两条容易诱发过度补偿：作者一旦意识到边界要说清，就在开头、边界节、报错表、结尾各说一遍"项目不联网、不上传"。读者第三次读到时不再理解成诚实，而是听成心虚。做法是把它收成正文末尾一节，说清不同环境下分别能干什么、不能干什么，其余位置不再重复。

film-curator 的例子：推荐由宿主 AI 客户端的模型做，客户端多半要联网。所以：

- ❌「不用注册，不用联网，不用装任何额外软件」
- ❌「项目本身不联网：不查片源，不上传数据。你的 AI 客户端要不要联网取决于客户端本身，跟这个项目无关」："跟这个项目无关"是甩锅，推荐这件事恰恰依赖它
- ❌ 归层归对了，但"项目自己不碰网络"在开头、"它不能做什么"、结尾各出现一次，共三处：读者会觉得作者在反复自证
- ✅ 收成末尾一节，按环境分档："装在能联网的 AI 客户端里，它是完整的：库内片单不够用时可以从片单之外给你新建议。装在不联网的环境里，比如本地部署的模型，它会缩到只吃本地数据：维护片单、记分、排计划、做统计、基于已存记录问答都照常，片单之外的推荐做不了。项目自己的代码任何时候都不联网。"

写完准备表后逐行自问：这一项是谁的需求？属于宿主的，说明它归宿主管，同时说清宿主承担了哪个功能。不要替宿主承诺，也不要假装读者不需要宿主。

分档时写清每档"能做什么"和"不能做什么"两侧，只写不能做的等于劝退，只写能做的等于隐瞒。每档控制在两三句，这是注意事项，不是功能矩阵。


## C6 · 语域检查

| | README | 售卖页 |
|---|---|---|
| 必须有 | 每步预期输出、失败出路、术语解释、支持渠道 | 证据层、风险消解、行动指令、不适合谁 |
| 必须无 | 促销腔、催促、夸张、无解释术语 | 悬空卖点、只有参数没有转译 |
| 允许的温度 | 可有欢迎语、致谢、"遇到问题随时找我" | — |

README 允许温度但不允许促销：
- ✅「感谢购买。下面每一步都配了你应该看到的画面，照着做就行。」
- ❌「立刻开启高效之旅！」

## C7 · 跨文档一致性（两类都生成时必跑）

1. 售卖页每条承诺 → 在 README 找到对应的可执行步骤或功能位置。找不到 = 退款风险，必须报出。
2. 售卖页「不适合谁」与 README「它不能做什么」不得矛盾。售卖页说支持、README 说不支持 → 严重不一致，停下报告。
3. 数字一致：价格、时长、数量、版本在两处必须相同。
4. 售卖页承诺的"几分钟上手" ≥ README 步骤数 × 合理耗时。承诺 3 分钟但 README 有 11 步 → 改承诺，不是改 README。
5. `双重` 模式下，README 分界线之上的说服语言不得比售卖页承诺更激进。

## C8 · 去 AI 痕迹（渲染后必跑）

正文成稿后整篇过一遍。**这一步必须真的执行改写**，不是只数一遍破折号个数就报"通过"。

按这个顺序找可用的规则：

1. 宿主装了 `humanizer` skill（在 `~/.claude/skills/humanizer/`，或客户端对应的 skill 目录）→ 调它，它的规则最细且会跟上游更新
2. 没装 → 读本目录的 `humanizer-zh.md`，它是随包副本，规则同源
3. 两个都读不到 → 按下表自查，这是最弱的一档

改完在回复里说清动了哪几处、为什么，以及哪些地方故意没动（技术细节、路径、报错原文、案例标本都不改）。

| 模式 | 例 | 改法 |
|---|---|---|
| 三段式惯性 | 凡列举都凑成三条 | 两条够就写两条 |
| 内联加粗标题列表 | `- **性能：** 性能得到提升` | 合并成句子，去掉粗体前缀 |
| 破折号过量 | 一段里两个以上 `——` | 改成逗号或断句 |
| 否定式排比 | "不仅是 X，而是 Y" | 直接说 Y |
| 系动词回避 | "作为一款…"、"拥有…特性" | 换成"是"、"有" |
| 虚假范围 | "从 A 到 B"而 A、B 不在同一尺度 | 直接列 |
| 同义词循环 | 同一事物换三种说法 | 统一叫法 |
| 抬升意义 | "标志着"、"体现了"、"凸显" | 删掉整句 |
| 通用积极结尾 | "开启高效之旅" | 删掉 |
| 句长均一 | 每句都 20 字上下 | 长短交替 |
| 引语块滥用 | 每个例句都用 `>` 单独起一段 | 短引语并进正文，用「」标出 |

判据：**读三段以上不觉得是模板**。做到了才算过。

- ❌ 只 grep 了 `——` 和 `- **` 的出现次数，数字是 0 就报"C8 已过"，一个字没改
- ✅ 逐段读一遍，改掉几十处破折号、几条内联加粗列表、几处句长过齐的段落，然后说明剩下的 `——` 为什么是故意的（它们本身是讲破折号规则的例句，改了就没样本了）

# 三、五 Persona 对抗自检（替代测试集，零素材成本）

生成后依次扮演，逐条回答，答不出即为缺陷。

**① 零基础读者，已付费**（交付型 README 主 persona）
- 第一步我要打开什么？在电脑哪里打开？
- 文里提到的每个界面、文件、导出物，我知道它在哪个路径吗？
- 有哪个词我不认识、文中又没解释？
- 文里给的每段命令，我知道它是干什么的、要不要我自己敲吗？
- 每一步做完，我怎么知道自己做对了？
- 到第一次真正用上它，我要做几步？超过三步的话，哪几步其实能让它自己做？
- 准备表里说"我一定已经有"的东西，万一我没有，文里给了核对方法和出路吗？
- 报错了，文里有没有告诉我怎么办？
- 我付的钱买到的东西，在这份文档里兑现了吗？
- 卡住了找谁？

**② 犹豫的买家**（售卖页主 persona）
- 凭什么信这几句话？证据在哪？
- 为什么不买更便宜的 / 为什么不将就现状？
- 买了不合适怎么办？
- 这是给我的，还是给所有人的？

**③ 竞品**（全部通用）
- 哪些句子我照抄也成立？（→ 全部重写）
- 哪些承诺我能证伪？

**④ 路过的非技术评估者**（公开型 / 双重 README 主 persona）
- 看完前三行，我能一句话转述给别人吗？
- 我看到结果长什么样了吗，还是只读到形容词？
- 我会在哪些地方用到它，只能跟 AI 说话，还是也有界面？文里说清了吗？
- 它一共能干几类事？我读完只记住一件事的话，是不是漏了？
- 我凭什么信这个能用、且半年后还有人管？
- 我要不要给 star / 要不要买，文档里有让我决定的信息吗？

**⑤ 挑刺的编辑**（全部通用，最后一道）
- 有哪个细节是作者编出来的？（数字、次数、工具名、场景）
- 有哪句话我要读两遍才懂？为什么，是缺上下文，还是用了圈内人的省略说法？
- 有哪个断言超出了作者能负责的范围？（替宿主环境、替第三方承诺、替读者的机器打包票）
- 反过来，有哪个断言在替读者省略真实成本？（宿主要联网/要账号，正文说成"不需要"）
- 有哪件事说了三遍？作者是在反复自证，还是真有必要重复？
- 哪几段读起来像模板？（三段式、内联加粗列表、破折号成串、句长均一）
