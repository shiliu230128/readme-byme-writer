# Core：素材地图 · 事实层 · 通用质量规则

本文件每次都加载。三部分：怎么捞素材（不让用户去找 case）、事实层长什么样、两类文案通用的质量规则。

---

# 一、素材：不让用户创造，只让他指路

写文案的人手上通常没有用户的真实生活细节，这是**素材缺口，不是表达缺口**。解决办法不是让用户「去找几个 case」，而是去素材已经存在的地方捞。

## 素材地图（按优先级自动读取）

**README 侧**

| 需要的信息 | 去哪里读 |
|---|---|
| 真实用法示例 | 测试文件（最好的示例来源）、`examples/`、demo 脚本 |
| 环境前置条件 | CI 配置（`.github/workflows/`）、Dockerfile、`package.json` engines、`pyproject.toml`、`.nvmrc`、`requirements.txt` |
| 依赖与版本约束 | 锁文件、manifest |
| 现成 FAQ 与报错 | issue 列表、客服或群聊记录、`CHANGELOG` 的 fix 条目、**代码里的错误信息字符串**（每一条 throw/raise 都是一个读者会看到的报错） |
| 配置项全表 | `.env.example`、config schema、命令行参数解析代码 |
| 入口与启动方式 | `package.json` scripts、`Makefile`、`main`/`__main__`、导出声明 |
| 可视化物料 | 现有截图、`docs/` 图片、demo 视频、社交媒体已发的图 |
| 许可证与维护信号 | LICENSE、commit 频率、tag 历史 |

**售卖页侧**

| 需要的信息 | 去哪里读 |
|---|---|
| 痛点原话 | 客服记录、售前咨询、退货原因、已有评价、社群提问 |
| 新品无自有素材时 | **竞品评论区的差评**，最浓缩的痛点库 |
| 硬参数 | 参数表、详情图、说明书、供应商资料 |
| 反对意见（写 FAQ 用） | 售前咨询里被问最多的几个问题 |
| 价值锚点 | 替代方案的成本（人工时间、竞品价、自己 DIY、什么都不做的持续损失） |

材料里读不出来的通常只有两件事：**给谁用**、**和什么比**。这两件才值得占用提问额度。

# 二、事实层结构

事实层把「产品是什么」与「怎么说」分离。同一份事实可渲染成 README、售卖页、落地页、投放文案。默认只存在于上下文里。

```markdown
# 事实层: <产品名>

## 身份
- 品类名词（读者已知的类别，不是自造词）:
- 读者技术水平: 零基础 | 会复制粘贴 | 开发者
- 使用场景与触发时刻:
- 价格 / 交付形态:
- 售卖页载体: 电商详情页 | 独立落地页 | 社群短文案

## 能力（每条是可被感知的结果，不是功能名）
- 结果: … | 依据: … | 出处: …

## 交付形态清单（README 用，逐项核对有没有）
命令行 / 跟 AI 对话 / 图形界面或网页 / 移动端 / 导出的文件 / 定时任务
每项有的话记下可定位路径。

## 入口清单（README 场景覆盖用，逐行打勾）
从意图路由表、CLI 子命令、UI 顶层导航、菜单项数出来，一行一条。

## 依据库
| 类型 | 内容 | 出处 | 可公开 |
|---|---|---|---|
| 参数 / 规格 / 机制 | | | |
| 检测 / 资质 | | | |
| 数量（销量 / 用户数 / 时长 / star） | | | |
| 用户原话（保留口语） | | | |
| 可视化物料（截图 / GIF / 前后对比） | | | |

## 边界（不支持什么 / 谁不该买 / 谁不该用）
- 事实: … | 后果: … | 替代建议: …

## 环境与前置（README 必填，逐条净室推演）
| 项 | 是否必需 | 版本约束 | 属于哪一层 | 零基础读者怎么弄到 | 要花钱吗 | 出处 |
|---|---|---|---|---|---|---|

「属于哪一层」填：产品自身 / 宿主环境 / 读者已有。

## 可预见的失败点（README 必填）
| 触发条件 | 读者屏幕上会看到的原话 | 怎么解决（含后果说明） |
|---|---|---|

## 替代方案（售卖页必填）
| 替代 | 它更适合的情况 | 我们更适合的情况 |
|---|---|---|
| 自己动手做 / DIY | | |
| 什么都不做 / 继续将就 | | |
| 竞品 A | | |

## 承诺-兑现（两类都写时必填）
| 售卖页承诺 | README 中的兑现位置 | 状态 |
|---|---|---|

## 缺口（只进回复，不进正文）
- 缺: … | 补了能修好: … | 正文当前怎么处理的（不写 / 通用做法 / 写轻）
```

# 三、通用质量规则

这些规则跨两类文案通用。它们**故意写成反面规则**：反面规则数量少、跨品类稳定；正向范例库要按品类无限堆积，永远不够，而且照着范例写最容易写出模板腔。

## 反证测试

把句子里的产品名或主语替换成**任意同类竞品**，句子还成立吗？成立就是零信息量，重写。

适用位置：定位句、痛点句、特色句、第一屏人群认领。

「基于先进架构的高性能数据处理框架」换成任何库都成立。「让你不用手写分页逻辑，就能给已有接口加上游标分页」换成别的就不成立。

## 具体度，以及反编造

任何承担说服职责的句子，至少含一个可核对的元素：数字、时间、地点、具体动作、型号、用户原话。一段里连续出现三个以上纯形容短语且没有可核对元素，就是模板腔。

**但具体度只能来自素材。** 这条要求会诱发一种失败：为了具体而编。编出来的细节比抽象表述更糟，抽象只是无效，编造是当场暴露作者没有真实素材。素材不够时，把句子退到素材支持的抽象层级。

「想要一份自己的观影记录，但用 Excel 记了三次就放弃的人」，如果 Excel 和「三次」是凭空填的，就退回到「想留一份自己的观影记录，但手动记表格总是记几次就断了」，保留行为，去掉假精确。

## 依据嵌在叙述里

有依据的地方，把依据写进句子，不另开一节列成表。检查的是「这句话能否被核对」，不是「有没有凑满几种依据类型」。

同一个理由的两种失败：

- 参数直接跳到体验，中间那环没了。「1200W 大功率，吹得又快又干」里读者不知道 1200W 意味着什么，补上「500ml 90 秒烧开」才通
- 为了补齐中间那环，每条都摊成「事实 → 结果 → 感受」三句，读起来像在背公式

前者缺信息，后者有结构强迫症。判断标准是读者读完知不知道你凭什么这么说，不是格式对不对。没依据的卖点不许占主卖点位，降级写轻，或者删掉。

## 缺口协议：缺口不进正文

质量最大的敌人不是写得差，是用模板腔把空白填满，看起来完整，实则空洞。但把 `[待确认]` 塞进正文也是错的：正文是给读者看的成品，读者不关心作者缺什么素材。

| 缺口类型 | 正文怎么办 | 例 |
|---|---|---|
| 缺了读者也不会卡住 | 整段不写 | 缺 star 数 → 不提数量 |
| 缺了读者一定卡住 | 写成读者能自己解决的通用做法 | 不知道客户端 skill 目录 → 写「在客户端设置页或文档里搜 skill / 扩展 / 插件」 |
| 缺的是承诺类信息 | 不写，等用户补 | 价格、联系方式、许可证 |

缺口清单**只出现在回复里**，格式：`缺什么 | 补了能修好什么`。

## 可懂度：能不能复述

上一条管「有没有信息」，这条管「读者能不能解码」。任何承担说服职责的句子，问：一个不熟悉这个产品的人读完，能不能复述出发生了什么？

「每周想看点什么，但每次挑片都花掉二十分钟，最后还是划走的人」，这句里「划走」是谁在划、划的是什么，读者要自己拼。改成「一打开视频软件就在片单里翻，翻了二十分钟最后关掉去刷手机」就不用拼了。

解释产品机制的句子要自带上下文，**先说机制，再说好处**。省掉机制只留好处，读者会卡在半句话上。最常见的失手是把机制压进破折号里：读者看到「它会把这片子好不好和我当时看得下去吗分成两个分数记」，不知道这两个分数是什么时候、由谁填的。先说清「记录看完时它会问两个分数」，再说分开记的理由。

## 禁用词

**两类都禁**（除非量化依据出现在同一句内）：
高性能、现代化、优雅、轻量级、强大、极致、领先、颠覆、赋能、闭环、深度融合、全方位、一站式、无缝、完美、海量、超强、智能化

**README 额外禁**：促销腔、催促语、无量化的最高级、「仅需一秒」类夸张、竞品贬损

**售卖页额外禁**：绝对化违规词（最、第一、国家级、100%、永久）、医疗功效暗示、伪造数量词

自己领域的高频废词（行业黑话之类）直接追加到上面这张表里。

## 非技术读者可读性（README 专用）

逐条检查：
- 每个技术名词首次出现处有没有一句白话解释？
- 有没有把「工程语言的优势」当卖点？「更现代的架构」对普通读者是零信息，要转译成「你不用再做什么」
- 有没有把命令行当默认路径而没给图形界面或 zip 替代？
- 每个代码块上方有没有一句「这行是干什么的」？裸命令对零基础读者是恐吓
- 有没有把只对维护者有意义的信号当卖点？测试通过数、代码行数、覆盖率、commit 数，普通读者无法评估，写进去只是噪音，还暴露作者在拿工程指标充数

## 依赖边界核对（防止说反话）

产品的依赖分三层，混在一起就会写出自相矛盾的句子：

| 层 | 例 |
|---|---|
| 产品自身 | 这个项目的代码要不要联网、要不要密钥 |
| 让它跑起来的宿主 | AI 客户端、浏览器、运行时。它们的联网和账号需求不由你决定 |
| 读者已有的东西 | 已经装好的客户端、已经有的账号 |

三条规则：

**凡写「不需要 X」，要限定到层。** 跨层断言就是错误陈述。

**宿主是产品核心功能的必要条件时，不许把宿主的需求说成「不需要」。** 判据：这个能力是谁提供的？靠宿主提供的，宿主的依赖就是读者的真实成本，不能藏。

**归清层之后只讲一次。** 前两条容易诱发过度补偿：作者一旦意识到边界要说清，就在开头、边界节、排查表、结尾各说一遍「项目不联网、不上传」。读者第三次读到时不再理解成诚实，而是听成心虚。做法是收成正文末尾一节，按环境分档说清分别能干什么、不能干什么，其余位置不再重复。

分档时两侧都写：只写不能做的等于劝退，只写能做的等于隐瞒。每档两三句，这是注意事项，不是功能矩阵。

一个真实的例子：某个影视推荐 skill，推荐这件事是由宿主 AI 客户端的模型做的，客户端多半要联网。所以「不用注册，不用联网，不用装任何额外软件」是错的；「你的客户端要不要联网跟这个项目无关」是甩锅，因为推荐恰恰依赖它。正确写法是收到末尾一节，按能联网 / 不能联网两档分别说清哪些功能照常、哪些做不了，最后补一句项目自己的代码任何时候都不联网。

## 语域检查

| | README | 售卖页 |
|---|---|---|
| 必须有 | 每步预期输出、失败出路、术语解释、支持渠道 | 依据、风险兜底、行动指令、不适合谁 |
| 必须无 | 促销腔、催促、夸张、无解释术语、卖点重述 | 悬空卖点、只有参数没有转译 |
| 允许的温度 | 可有欢迎语、致谢、「遇到问题随时找我」 | — |

README 允许温度但不允许促销。「感谢购买，下面每一步都配了你应该看到的画面，照着做就行」可以；「立刻开启高效之旅」不行。

## 跨文档一致性（两类都生成时必跑）

1. 售卖页每条承诺，在 README 里找到对应的可执行步骤或功能位置。找不到 = 退款风险，要报出来
2. 售卖页「不适合谁」与 README「它不能做什么」不得矛盾。一处说支持一处说不支持 → 停下报告
3. 价格、时长、数量、版本在两处保持一致
4. 售卖页承诺的上手时间 ≥ README 步骤数 × 合理耗时。承诺 3 分钟但 README 有 11 步 → 改承诺，不是改 README

## 去 AI 痕迹（成稿后必跑）

这一步的规则不在本文件里。按 SKILL.md Step 5 的顺序找：宿主装了 `humanizer` skill 就调它，没装就读本目录的 `humanizer-zh.md`（同源随包副本）。两个都读不到才用下面这张最弱的表自查。

| 模式 | 例 | 改法 |
|---|---|---|
| 三段式惯性 | 凡列举都凑成三条 | 两条够就写两条 |
| 内联加粗标题列表 | `- **性能：** 性能得到提升` | 合并成句子，去掉粗体前缀 |
| 破折号过量 | 一段里两个以上 `——` | 改成逗号或断句 |
| 否定式排比 | 「不仅是 X，而是 Y」 | 直接说 Y |
| 系动词回避 | 「作为一款…」「拥有…特性」 | 换成「是」「有」 |
| 虚假范围 | 「从 A 到 B」而 A、B 不在同一尺度 | 直接列 |
| 同义词循环 | 同一事物换三种说法 | 统一叫法 |
| 抬升意义 | 「标志着」「体现了」「凸显」 | 删掉整句 |
| 通用积极结尾 | 「开启高效之旅」 | 删掉 |
| 句长均一 | 每句都 20 字上下 | 长短交替 |
| 引语块滥用 | 每个例句都用 `>` 单独起一段 | 短引语并进正文，用「」标出 |
| 正反对照成瘾 | 每条规则都配一组 ❌/✅ | 只在对比本身有信息量时留，其余化进叙述 |

判据：**读三段以上不觉得是模板**。只 grep 一遍 `——` 的个数、数字是 0 就报通过，一个字没改，这不算跑过这一步。

不改的东西：路径、命令、报错原文、以及故意留作反例的句子。改完在回复里说清动了哪几处、哪些故意没动。

# 四、Persona 自检

生成后依次扮演，逐条回答，答不出即为缺陷。

**① 零基础读者，已付费**（README 主 persona）
- 第一步我要打开什么？在电脑哪里打开？
- 文里提到的每个界面、文件、导出物，我知道它在哪个路径吗？
- 有哪个词我不认识、文中又没解释？
- 文里给的每段命令，我知道它是干什么的、要不要我自己敲吗？
- 每一步做完，我怎么知道自己做对了？
- 到第一次真正用上它，我要做几步？超过三步的话，哪几步其实能让它自己做？
- 准备表里说「我一定已经有」的东西，万一我没有，文里给了核对方法和出路吗？
- 首选路径失效了，还有别的路吗？
- 报错了，文里有没有告诉我怎么办？
- 这个文件夹里哪些是我的东西、哪些别碰？
- 卡住了找谁？

**② 犹豫的买家**（售卖页主 persona）
- 凭什么信这几句话？依据在哪？
- 为什么不买更便宜的？为什么不将就现状？
- 买了不合适怎么办？
- 这是给我的，还是给所有人的？

**③ 挑刺的编辑**（两类通用，最后一道）
- 有哪个细节是作者编出来的？（数字、次数、工具名、场景）
- 有哪句话我要读两遍才懂？是缺上下文，还是用了圈内人的省略说法？
- 有哪个断言超出了作者能负责的范围？（替宿主环境、替第三方承诺、替读者的机器打包票）
- 反过来，有哪个断言在替读者省略真实成本？
- 有哪件事说了三遍？是反复自证，还是真有必要重复？
- 哪几段读起来像模板？（三段式、内联加粗列表、破折号成串、句长均一、正反对照成排）

**④ 竞品**（两类通用）
- 哪些句子我照抄也成立？（→ 全部重写）
- 哪些承诺我能证伪？
