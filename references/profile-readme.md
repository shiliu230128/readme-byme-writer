# Profile · README（说明书）

**读者已经决定要用它了，只想跑通。而且可能完全不懂技术。**

写好的判据只有一条：一个不写代码的普通人，照着这份文档做，能不能成。所以这里不写竞品对比、不求 star、不重述卖点，那些是售卖页的活，混进来只会挤掉第一步。

结构固定三段：**这是什么 → 怎么用 → 项目架构**。顺序不能换，因为读者的问题就是这个顺序来的。

---

## 一、这是什么

### 一句话概述

首句要能被直接复制到聊天窗口发给朋友，对方不需要补充说明就懂。

参考句式：`<产品名> 让你 <可验证结果>，不用 <原本的麻烦事>`。句式是脚手架，通顺更重要，别为了套格式写出别扭的话。

两条硬要求：
- 过反证测试：把产品名换成任意同类产品后句子仍然成立 → 这句零信息量，重写
- 不用实现方式定位。「基于 X 的 Y 框架」是给工程师看的，对普通读者是噪音

### 交付形态要齐全

开头三段之内，把**读者会接触到的所有形态**都提一次。少提一个，读者就不知道它存在。

逐项核对产品有没有：命令行、跟 AI 对话、图形界面或网页、移动端、导出的文件、定时任务。有的都要出现在开头。

而且每个界面、文件、导出物第一次出现时就给出可定位路径。「网页上也能点」这种说法不给路径，读者要么去翻文件夹，要么当它不存在。路径要一跳到位：写 `film-curator/web/index.html`，别写「进项目里的 web 文件夹，双击 index.html」，那是两跳，读者得先找 web 在哪。

判据：读者读完开头，能不能列出「我会在哪些地方用到它」。列不全就不合格。

### 典型使用场景

覆盖**产品的全部主要入口**，不是挑一个最好演示的写。

做法是先从素材里数出产品声明支持的意图类别（意图路由表、CLI 子命令、UI 顶层导航、菜单项），逐行打勾，再归并成 2-4 个用户视角的场景。常见失手是数到一半就开始写，把不像主线的功能顺手丢掉，读者于是以为它只能干一件事。

每个场景说清两件事：用户实际说什么或点什么（用原话、原按钮名），以及这件事**有几条操作路径**（只能跟 AI 说？也能在界面上做？两条都写）。

**每个场景 3-5 行封顶。** 覆盖全比写透一个更重要，写长了会挤掉安装部分。

### 输出示例

紧跟着放证据：截图、GIF、输出片段、前后对比。普通读者无法从文字描述里想象结果，看到画面才会继续读。

没有任何可视化物料时，用「你说 X → 它做 Y」的对话演示顶上，同时在回复里把截图列为最高优先级缺口，并告诉用户拍什么（一张跑通后的结果截图就够，不要求他做设计）。正文里不留空占位，不写「此处待补截图」。

## 二、怎么用（本 profile 最重的部分）

### 2.1 开始之前你需要准备什么

一张表，不是一段话：

| 需要什么 | 你可能已经有了吗 | 怎么弄到 | 要花钱吗 |
|---|---|---|---|

填表前先做**净室推演**，这是保证读者不卡住的核心机制：

> 假设读者是一台刚装好系统的电脑 + 一个没写过代码的人。逐条走每个命令，问：这条命令要成功，机器上必须已经存在什么？

逐项核对（每项给出「有 / 无 / 已在文中说明」）：运行时及**具体版本**、包管理器、git **或下载 zip 的替代路径**（不会用 git 的人必须有另一条路）、系统级依赖（编译器、ffmpeg、字体、数据库）、密钥或账号（是否收费、去哪申请、多久批下来）、网络条件、操作系统差异、端口占用与权限、路径里的中文或空格。

任何一项没在正文出现就补一行。无法确认的按 core.md 的缺口协议处理。

三条填表规则：

**归层。** 每行标出这一项是**产品自身**的需求、**宿主环境**的需求，还是**读者已有**的东西。归错层会写出两种反向错误：替宿主乱承诺，或替读者隐瞒真实成本。宿主的需求写成「取决于你用的 X」，并说清宿主承担了哪个功能。详见 core.md 的依赖边界核对。

**只留会变的行。** 表里只列读者可能没有、需要动手弄的项。人人都有的（浏览器、操作系统）和产品不需要的，合并成一句话带过。判据：一行的三列里有两列是「不需要」或「—」，这行就该并进那句话里。

**别替读者的机器打包票。** 「某系统一定自带 X」这类断言几乎总是错的，系统版本、精简安装、企业镜像都会让它不成立。而它一旦错，读者第一步就卡住且不知道为什么。做法是换成一句让读者当场验证的话，验证不通过再给出路。能让 AI 代跑的验证写成「让 AI 跑一句 X」，不要让读者自己开终端。

比如 macOS 从 12.3 起就不带 `python` 命令了，`/usr/bin/python3` 在很多机器上只是个占位符，点了才触发安装开发者工具。所以表里该写「都要自己确认一下，Mac 也不例外」，正文补一句怎么确认、没有的话去哪装。

### 2.2 最快的上手方式

**先定最短路径，再写步骤。** 常见错误是把维护者的完整流程当成读者的必经之路，写出十步「快速上手」。

写步骤前先问三个问题，能删的删掉：

| 问题 | 处理 |
|---|---|
| 这一步能不能让 AI / 安装器 / 脚本代做？ | 能 → 作为**首选路径**放最前，手动步骤降级为「想自己动手」分支 |
| 这一步是首次使用必须，还是出问题时才需要？ | 后者 → 移到排查表，不占正文步骤 |
| 这一步做不做，读者第一次使用会不会失败？ | 不会 → 删掉或后置 |

判据：**首次跑通的步骤 ≤ 3 步。** 超了就说明有步骤该被合并、代做或后置。初始化、生成配置、验证环境这类通常能由程序首次运行时自己完成，或由 AI 代做，不该让读者手打。

产品跑在 AI 助手里时，首选路径就是让 AI 装：给一句可直接粘贴的自然语言指令，而不是让读者去找目录、复制文件夹。

每步要有三样信息：**在哪做**（终端 / 浏览器 / 文件夹，写清位置）、**做什么**（可直接复制的命令或操作，一次一个动作）、**你应该看到**（具体的成功信号）。

三样信息缺一不可，但形式可以化开。只有一两步时写成两句话，比套编号格式更轻。

几条配套约束：

- **每步都要有「你应该看到」**，普通读者无法自行判断一步是否成功。最后一步的成功信号要用产品的真实效果，不是命令的输出：「它给你推荐了就是装好了」优于「终端打印了一段 JSON」
- **一步只放一个需要判断的动作**。「安装依赖并配置环境变量」拆成两步
- **术语就地解释**。不写「配置环境变量 `API_KEY`」，写「打开项目里的 `.env` 文件（用记事本或任何文本编辑器都行），把 `API_KEY=` 后面换成你的密钥」
- **Windows 和 Mac 分别给命令**。涉及终端命令、路径分隔符、文件显示的地方只写一套 = 一半读者卡住
- **代码块上方一句话说清它是干什么的**，必要时说清要不要执行。裸命令对零基础读者是恐吓。可代做的写成「让 AI 跑一次 X（它会做 Y）」，命令本身放括号里
- **安装位置给全路径**。已知的主流客户端列成表（客户端 × Mac 路径 × Windows 路径），再补一句「用别的客户端就去它的设置页或文档里搜 skill、扩展、插件」，以及一句「`~` 是什么、Finder 里怎么跳过去」。只写一家的路径，别的客户端用户会直接放弃

### 2.3 手动方式

首选路径失效时的退路：不用 AI 代做、不用脚本，纯手工怎么装。同样给全路径和成功信号。

这一节存在的意义是兜底。首选路径依赖的东西（AI 客户端、安装脚本、网络）任何一环出问题，读者都还有路可走。

### 2.4 出问题怎么办

排查表和 FAQ 合成一张，因为读者的处境是同一个：卡住了。

第一列要写**屏幕上出现的原话**，不是描述：

| 你看到 | 意思是 | 怎么解决 |
|---|---|---|
| `command not found: node` | 电脑上还没装 Node | 回到准备表第 1 行 |

覆盖率要求：代码里每条会抛给用户的错误信息，以及准备表每一项缺失时的表现，都要有对应行。数量不足时在回复里报覆盖了几条、还差什么。

「怎么解决」那一列也要说清后果。不写「重新跑一次第 3 步的 `init`」，读者不知道 init 干什么、会不会覆盖自己的记录；写「让 AI 跑一次初始化把缺的文件建回来（`python3 scripts/xxx.py init`，只补缺的，不动已有的）」。

### 2.5 它不能做什么

3-5 条。看起来减分，实际是降退款率、提可信度的主力。

### 2.6 卡住了找谁

联系方式、响应时间、更新与售后说明、许可证（能不能商用、能不能转卖）。这些是承诺类信息，没确认就不写，缺口进回复。

## 三、项目架构

目录和文件的作用，但**按读者视角归类，不按工程视角**。读者关心的不是模块划分，是「哪些是我的东西，哪些别碰」。

三类分开写。**你的数据**是记录、配置、导出物，可以自己打开看、自己改、自己备份。**程序本体**是跑起来靠的东西，不用懂，也不用动。**改行为的地方**是想调整规则时该动哪个文件。

如果产品是给别人二次修改的（比如 skill、模板），这一节要说清改哪个文件影响什么、哪个文件别改（比如外部项目的副本、会被覆盖的生成物）。

普通读者向的产品，这一节写十行内就够。它的作用是让人不害怕这个文件夹，不是给出完整的架构说明。

## 自检清单

**这是什么**
- [ ] 首句可直接转述，过反证测试，没用实现方式定位
- [ ] 所有交付形态（网页 / 命令行 / 对话 / 导出文件 / 定时任务）在开头都提到了
- [ ] 每个界面、文件、导出物第一次出现时给了一跳到位的路径
- [ ] 入口清单逐行打过勾，每行都能指到正文某个场景；每个场景写了有几条操作路径，且 ≤5 行
- [ ] 有效果示例；没有的话已用对话演示顶上，截图缺口在回复里报了

**怎么用**
- [ ] 净室推演逐项走完；每项已归层；表里无两列都是「不需要 / —」的行；没有「某系统一定自带」式断言
- [ ] 首次跑通 ≤ 3 步；可代做的已改为首选路径；只在出错时才需要的已移进排查表
- [ ] 每步都有「你应该看到」，最后一步用真实效果而非命令输出
- [ ] 无一步多动作；术语首次出现都解释了；双系统命令齐备
- [ ] 每个代码块上方说清了作用和要不要执行
- [ ] 主流客户端路径已列成表，另给通用找法
- [ ] 有手动方式作为退路
- [ ] 排查表覆盖已知报错，「怎么解决」说清了后果
- [ ] 有「它不能做什么」；联系方式与许可有则写、无则整节不写并把缺口报出

**项目架构**
- [ ] 按「你的数据 / 程序本体 / 改行为的地方」归类，不是模块图
- [ ] 说清了哪些文件别碰

**通篇**
- [ ] 没有促销腔、没有卖点重述、没有竞品对比、没有 star 请求（这些归售卖页）
- [ ] 有具体度，且没有为了具体而编的细节（数字、次数、工具名）
- [ ] 正文里没有 `[待确认]` 和空占位
- [ ] 依赖已归层：既没替宿主承诺，也没把宿主的成本说成「不需要」；同一条边界只在一处讲
- [ ] 去 AI 痕迹已真的改写过（优先调 humanizer skill，没装则读 `humanizer-zh.md`）
- [ ] persona ①（零基础读者）和 ③（挑刺的编辑）的问题都答得出
