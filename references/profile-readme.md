# Profile · README（三种模式）

**共同前提：读者可能完全不懂技术。** 不假设读者知道终端、Node、包管理器、环境变量、clone 是什么。

但 README 有两种截然不同的读者，动作和信任机制都不同，必须先定模式，不能混写。

| 模式 | 读者 | 状态 | 要促成的动作 | 首屏归谁 |
|---|---|---|---|---|
| `交付型` | 已付费买家（私有仓库/发链接） | 已决定，只想跑通 | 独立安装成功、不来退款 | 跑通 |
| `公开型` | 路过的人，未付费 | 未决定，默认关页面 | 给 star / 试一次 / 想买 | 说服 |
| `双重` | 两者共用一个公开仓库 | 混合 | 上半说服，下半交付 | 分层 |

`双重` 是你的常见情况（公开仓库 + 售卖），它有个内在冲突：说服想占首屏，交付也想占首屏。解决办法见 R8，不要靠"写得兼顾一点"。

## 一、`公开型` 独有部分（面向未决策者）

### P1 · 一句话可转述测试

首句必须能被直接复制到聊天窗口发给朋友，对方不需要任何补充说明就懂这是什么。

强制句式：
```
<产品名> 让你 <可验证结果>，不用 <原本的麻烦事>。
```

规则：
- 过 C1 反证测试（换成任意同类产品后不成立）
- 品类名词必须是读者已知的类别，不能是自造词
- 禁止用实现方式定位（"基于 X 的 Y 框架"是给工程师的写法，对非技术读者是噪音）

### P1a · 交付形态齐全

开头三段之内必须把**读者会接触到的所有形态**都提到一次。少提一个，读者就不知道它存在。

清单：命令行 / 对话交互 / 图形界面或网页 / 移动端 / 导出的文件 / 定时任务。逐项核对产品有没有，有的必须出现在开头。

- ❌「它会记住你的口味、你的禁区、你这周还有几个空档，然后给你有理由的答案，并且把你看过什么、打了几分都存在你自己的电脑上」：项目带一个可交互网页，读者从这句里完全看不出来
- ✅「…你直接用中文跟 AI 说话。项目里还带一个本地网页，路径是 `film-curator/web/index.html`，双击就能打开」

判据：读者读完开头，能不能列出"我会在哪些地方用到它"。列不全 = 不合格。

规则 **P1b · 提到界面就给到路径**：正文每次提到某个界面、文件或导出物，第一次出现时给出可定位的路径，后面重复提到时再带一次也不算啰嗦。「网页上也能点」这类说法不给路径，读者要么去翻文件夹，要么当它不存在。

- ❌「网页上也能自己排：观影计划那栏有本周、本月、本季三个页签」：网页在哪？读者得自己去项目里翻
- ❌「进项目里的 `web` 文件夹，双击 `index.html`」：拆成两跳，读者要先找 `web` 在哪
- ✅「打开 `film-curator/web/index.html`，观影计划那栏有本周、本月、本季三个页签」


### P2 · 效果先于说明

首句之后立刻放证据：截图、GIF、输出片段、前后对比。非技术读者无法从文字描述里想象结果，看到画面才会继续往下读。

规则：如果没有任何可视化物料，改用**逐场景对话演示**（"你说 X → 它做 Y"）顶上，同时在回复里把截图列为最高优先级缺口。告诉用户拍什么（一张跑通后的结果截图即可），不要求他做设计。正文里不留空占位。

### P2a · 场景覆盖率（最容易漏的一条）

"它用起来什么样"这一节必须覆盖**产品的全部主要入口**，不是挑一个最好演示的写。

做法：从素材里数出产品声明支持的意图类别（意图路由表、CLI 子命令分组、UI 的顶层导航、菜单项），归并成 2-4 个用户视角的场景，每个都写。

**先数够，再归并。** 常见失手是数到一半就开始写：意图路由表有七行，只挑了前六行归并成三个场景，剩下的"赏析""统计"因为不像主线功能被顺手丢掉。判据是把路由表逐行打勾，每一行都要能指到正文的某个场景里。

每个场景必须回答两件事：
- 用户实际说什么 / 点什么（原话或原按钮名）
- 这个场景**有几条操作路径**（只能跟 AI 说？也能在界面上做？两条都写）

**每个场景 3-5 行封顶。** 覆盖全比写透一个更重要，写长了会挤掉后面的安装部分。

- ❌ 只演示了"今晚看什么"一个场景，写了三段。读者以为它只能干这一件事，不知道还能排月度计划、还能在网页上直接改记录
- ❌ 写了三个场景，覆盖了意图路由表七行里的五行，漏掉"赏析"和"查询统计"。读者不知道看完还能跟它聊、还能回头查自己这个月看了什么
- ✅ 四小节：不知道看什么（说一句 → 它怎么筛 → 给什么）／排周月季计划（说一句 → 按周分配留机动位 → 网页上也能点）／维护影视库（跟 AI 说的三种话 + 网页上能点的四件事）／看完想聊或想看统计（先确认剧透边界 + 统计排除示例数据 + 网页上也有一栏）

判据：把素材里的入口清单逐行打勾，有任何一行在正文里指不到位置 → 不合格。


### P3 · 适合谁 / 不适合谁

两组，各 2-3 条。「不适合谁」不可省：公开型 README 里，敢写边界是最强的可信信号，非技术读者尤其靠这个判断"这人是不是在忽悠我"。

标题写「不适合谁」，别写「不给谁用」。后者把作者摆成了发放许可的一方，读者读到的是拒绝，而不是帮他自己判断。


### P4 · 为什么不用别的（非技术版）

这一节在交付型里没有，公开型必须有。但关键限制：

> **不能用工程语言论证差异，只能用"你不用再做什么"论证。**

- ❌「比 X 快 3 倍，架构更现代」（非技术读者无法评估，也不关心）
- ✅「同类工具要你自己配服务器，这个双击就能开」

强制列 ≥3 个替代，每个必须填"它更适合的情况"：

| 替代 | 它更适合 | 这个更适合 |
|---|---|---|
| 自己动手做 | | |
| 什么都不做 / 继续将就 | | |
| 竞品 A | | |

规则 **P4a**：任一替代写不出它的优势场景 → 停下，说明取舍没想清楚。诚实承认竞品在某些情况更好会提升可信度，不会掉转化。

### P5 · star 请求

最多出现一次，一句话，放在效果图之后或文档末尾。不重复、不加感叹号、不写"求"。

### P6 · 项目健康信号（只写读者能评估的）

许可证（能不能商用）、怎么提问、维护状态。

**禁止把维护者信号当健康信号。** 测试通过数、代码行数、覆盖率、commit 数，非技术读者无法评估这些，写进去只是噪音，还会暴露作者在拿工程指标充当卖点。这些属于开发者向 README（本 profile 不覆盖）。

- ❌「项目状态：44 个 Python 单元测试加 4 组前端测试全部通过；Python 3.9.6 实测可用；数据存放在 6 个文本文件」：前两条读者无法评估，第三条属于"你的东西存在哪"那一节
- ✅ 整节不写。许可证和联系方式没确认时也不写，缺口进回复

写不出读者能评估的健康信号时，整节不写，别用维护者数据凑一节出来。

## 二、`交付型` 独有前提

传统 README 优化"我该不该用它"，交付型优化"我照着做能不能成"。失败形态不同：前者失败 = 少一个 star；后者失败 = 一次退款和一条差评。

`交付型` 不写 P4（买家已经付钱，不需要再被说服选择）、不写 P5。

开头写「你买到的是什么」，2-3 句：

```
<产品名> 帮你 <可验证结果>，你不需要 <原本的麻烦事>。
装好之后你会得到：<一个具体画面>。
```

「一个具体画面」是核心。不是功能列表，是跑通后屏幕上出现什么、手上多了什么文件、省掉了哪个动作。

## 三、两种模式共有的交付部分（本 profile 最重的地方）

### 3.1 开始之前你需要准备什么

一张表，不是一段话：

| 需要什么 | 你可能已经有了吗 | 怎么弄到 | 要花钱吗 |
|---|---|---|---|

规则 **R2 · 净室推演（本 profile 最关键的机制）**：

> 假设读者是一台刚装好系统的电脑 + 一个没写过代码的人。逐条走每个命令，问：这条命令要成功，机器上必须已经存在什么？

逐项核对（每项给出"有 / 无 / 已在文中说明"）：
- 运行时（Node / Python / Java…）及**具体版本**
- 包管理器
- git **或下载 zip 的替代路径**（非技术读者往往不会用 git，必须给 zip 那条路）
- 系统级依赖（编译器、ffmpeg、字体、数据库）
- 密钥 / API key / 账号（是否收费、去哪申请、多久批下来）
- 网络条件（是否需要访问外网）
- 操作系统差异（Windows 与 Mac 命令不同）
- 端口占用、权限、路径里的中文或空格

任何一项未在正文出现 → **强制补一行**。无法确认的按 C4 处理：能写通用做法的写通用做法，不能写的整项删掉，缺口放回复里。

规则 **R2a · 每项归层**：填表时逐行标出这一项是**产品自身**的需求、**宿主环境**的需求，还是**读者已有**的东西（见 core.md C5c）。归错层会写出两种反向错误：替宿主乱承诺，或替读者隐瞒真实成本。宿主的需求写成"取决于你用的 X"，并说清宿主承担了哪个功能。

规则 **R2b · 表只留会变的行**：准备表只列读者**可能没有、需要动手弄**的项。人人都有的（浏览器、操作系统）和产品不需要的，不各占一行；不需要的项合并成一句话带过。

- ❌ 七行表，其中四行是「网络：不需要 / —」「账号或 API key：不需要 / —」「git：不需要 / —」「浏览器：一定有 / —」
- ✅ 三行表（客户端、Python 3、浏览器）+ 一句"不需要 git，不需要装任何第三方 Python 包，这个项目自己不需要账号和 API 密钥"

判据：一行的三列里有两列是"不需要"或"—"，这行就该合并进那句话。

规则 **R2c · 别替读者的机器打包票**：准备表的"你可能已经有了吗"一列，只写读者能自己核对的判断方法，不写你对他机器状态的猜测。"某系统一定自带 X"这类断言几乎总是错的，系统版本、精简安装、企业镜像都会让它不成立，而它一旦错，读者会在第一步就卡住并且不知道为什么。

做法：把"一定有"换成一句让读者当场验证的话，验证不通过再给两条出路。能让 AI 代跑的验证命令写成"让 AI 跑一句 X"，不要让读者自己开终端。

- ❌「Python 3：Mac 一定自带；Windows 通常要自己装」：macOS 从 12.3 起就不带 python 命令了，`/usr/bin/python3` 在很多机器上只是个占位符，点了才触发安装开发者工具。照这句写，Mac 用户会以为自己不用管
- ✅ 表里写「都要自己确认一下，Mac 也不例外」，正文补一段：让 AI 跑一句 `python3 --version`，打印出版本号就有了；没有的话 Mac 上可能弹窗提示装命令行开发者工具，点安装即可，也可以去 python.org 下载安装包


### 3.2 跟着做

**先定最短路径，再写步骤。** 常见错误是把维护者的完整流程当成读者的必经之路，写出十步"快速上手"。

规则 **R4a · 最短路径优先**：写步骤前先问三个问题，能删的删掉。

| 问题 | 处理 |
|---|---|
| 这一步能不能让 AI / 安装器 / 脚本代做？ | 能 → 把它作为**首选路径**放最前面，手动步骤降级为"想自己动手"分支 |
| 这一步是首次使用必须，还是出问题时才需要？ | 后者 → 移到报错表，不占正文步骤 |
| 这一步做不做，读者第一次使用会不会失败？ | 不会 → 删掉或移到后面的独立小节 |

判据：**首次跑通的步骤 ≤ 3 步。**超了就说明有步骤该被合并、代做或后置。初始化、生成配置、验证环境这类通常能由程序自己在首次运行时完成，或由 AI 代做，不该让读者手打。

产品跑在 AI 助手里时，首选路径就是让 AI 装：给一句可直接粘贴的自然语言指令，而不是让读者去找目录、复制文件夹。

- ❌ 四步：复制文件夹 → 开终端确认 Python 版本 → `cd` 进项目再跑 `init` 建数据文件 → 回到 AI 里说话。其中第 2、3 步只在出问题时才需要，却占了正文一半
- ✅ 两步：下载文件夹 → 跟 AI 说"把这个文件夹装成 skill"。Python 版本进准备表，`init` 进报错表（只有报 `Missing data file` 时才用得上）


每步固定三件套，**缺一即不合格**：

```
第 N 步 · <动作>
在哪做：<终端 / 浏览器 / 文件夹，写清位置>
做什么：<可直接复制的命令或操作，一次一个动作>
你应该看到：<具体的成功信号>
```

步骤只有一两步时不必套编号格式，写成两句话更轻。三件套的**信息**必须在，形式可以化开。

- **R3 · 可验证性闸门**：任何一步没有"你应该看到"，标为不可验证，必须补。非技术读者无法自行判断一步是否成功。最后一步的成功信号要用产品的**真实效果**，不是命令的输出（"它给你推荐了就是装好了"优于"终端打印了一段 JSON"）。
- **R4 · 单动作原则**：一步不能塞两个需要判断的动作。「安装依赖并配置环境变量」→ 拆两步。
- **R5 · 术语就地解释**：首次出现的技术名词当场用一句白话解释或换成白话。用 core.md 表 4 逐条核对。
  - ❌「配置环境变量 `API_KEY`」
  - ✅「打开项目里的 `.env` 文件（用记事本或任何文本编辑器都行），把 `API_KEY=` 后面换成你的密钥」
- **R6 · Windows/Mac 分叉**：涉及终端命令、路径分隔符、文件显示的地方两个系统分别给出。只写一套 = 一半读者卡住。
- **R9 · 命令自解释**：正文里每个代码块，上方一句说清"这行是干什么的"，必要时说清"你要不要执行它"。裸命令对零基础读者是恐吓。可代做的命令写成"让 AI 跑一次 X（它会做 Y）"，把命令本身放括号里，而不是让读者对着终端手打。
  - ❌ 报错表里写「重新跑一次第 3 步的 `init`」：读者不知道 init 干什么、会不会覆盖自己的记录
  - ✅「让 AI 跑一次初始化把缺的文件建回来（`python3 scripts/film_curator.py init`，只补缺的，不动已有的）」

- **R10 · 安装位置：给全路径，别让读者去找**。已知的主流客户端直接列成表（客户端 × Mac 路径 × Windows 路径），再补一句"用别的客户端就去它的设置页或文档里搜 skill、扩展、插件"。
  - ❌「找到你的 AI 客户端存放 skill 的目录」：读者不知道去哪找，卡在第一步
  - ❌ 只写 `~/.claude/skills/` 一家，别的客户端用户直接放弃
  - ✅ 三行表列出 Claude Code / Claude 桌面版 / Ducc 的 Mac 与 Windows 路径 + 一句通用找法 + 一句"`~` 是什么、Finder 里怎么跳过去"


### 3.3 常见问题与报错怎么办（主线内容，不是附录）

第二列必须是**屏幕上出现的原话**，不是描述：

| 你看到 | 意思是 | 怎么解决 |
|---|---|---|
| `command not found: node` | 电脑上还没装 Node | 回到"准备什么"第 1 行 |

规则 **R7 · 报错覆盖率**：代码里每条会抛给用户的错误信息，以及前置条件表每一项缺失时的表现，都要有对应行。数量不足时报告覆盖了几条、还差什么。

### 3.4 它不能做什么

3-5 条。看起来减分，实际是降退款率、提可信度的主力。

### 3.5 卡住了找谁

联系方式、响应时间、更新与售后说明、许可证（能不能商用、能不能转卖）。

## 四、`双重` 模式的分层规则

规则 **R8 · 硬分界线**：

文档分成说服段和交付段，**分界靠常规小节标题实现**。

- ✅ 上半段末尾是「为什么不用别的」，紧接一个 `## 安装`
- ❌ `## 上面是它是什么，下面是怎么装`
- ❌ `## 以下开始安装部分`、`## 前面讲完了，接下来是操作步骤`

不合格的那几个错在同一处：标题在讲这份文档的结构，不在讲产品。读者不需要被告知"你现在读到分界了"，一个 `## 安装` 已经完成同样的切换，而且看起来是正常的开源项目。同理，不用水平分割线充当分界。


分界的约束靠内容执行，不靠标题喊出来：
- 分界线**之前**：不出现任何命令、任何终端截图。只有 P1–P4、效果图。
- 分界线**之后**：不出现任何说服性语言、不出现卖点重述、不出现 star 请求。只有步骤和参考信息。

理由：两种语域混在一起会双向损伤。未决策者被安装细节赶走，已付费者在说服话术里找不到第一步。

购买入口放在分界线之前的末尾，一次，一句话。
