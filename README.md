# product-copy

给 AI 助手装的一套文案本领。你指一个项目或说几句产品情况，它产出两类东西：面向非技术读者的 GitHub README，或者商品售卖页描述。

两类文案的本质不同，所以规则是分开的。README 是说明书，读者已经决定要用它了，只想跑通，判据是一个不写代码的普通人照着做能不能成。售卖页是营销，读者还没决定，默认动作是划走，判据是他能不能认出「这是给我的」。

它跟直接让 AI「写个 README」的区别是：先建事实层再渲染。没有依据的地方不用形容词填，也不在正文里留占位标记。该整段不写就不写，该改成通用做法就改。缺什么信息、补上能修好什么，它在回复里单独告诉你。

## 安装

把这个文件夹复制到 AI 客户端的 skill 目录：

```bash
cp -r ~/Desktop/product-copy ~/.claude/skills/product-copy
```

Claude Code 的目录是 `~/.claude/skills/`；其他客户端见各自文档。

## 怎么用

直接说话，不用记命令：

```
给桌面的 film-curator 写个 README
给这个项目写一份卖货用的详情页文案
两个都要，先售卖页
```

它会先自动读项目里能读的东西，只在真的推不出来时问你几个问题（上限 5 个，一次问完，每个都附带「你不答我按 X 处理」）。

## 你会拿到什么

默认只有正文一个文件。

README 写进项目根目录；目标位置已有 README.md 时不覆盖，写成 `README.draft.md` 让你自己替换。售卖页写到 `~/Desktop/<产品名>-copy/`。

自检结果不写成文件，直接在回复里告诉你哪几条没过、缺什么信息能补好。

想要中间产物就明说「把事实层也给我」，它会写到 `.product-copy/` 子目录里。`facts.md` 是事实层，记着能力、边界、前置条件、可预见报错，每条带出处；之后还要写落地页、小红书时能复用，不必重新摄取。`review.md` 是完整自检报告，只在你要求时才生成。

## 可以配置什么

在输出目录放一个 `.product-copy/config.json`：

```json
{
  "outputDir": "~/Desktop/copy-drafts",
  "keepIntermediates": true
}
```

`outputDir` 改默认输出位置，`keepIntermediates` 设为 true 则每次都保留中间产物。

指令里直接说「写到 xxx」优先级最高，会盖过配置文件。

## README 写成什么样

固定三段，顺序不换，因为读者的问题就是这个顺序来的。

**这是什么**：一句话概述（能直接复制发给朋友那种）+ 典型使用场景 + 输出示例。场景要覆盖产品的全部主要入口，不是挑一个最好演示的写。常见失手是只演示了一个功能，读者以为它就只能干这一件事。

**怎么用**：先给一张「开始之前你需要准备什么」的表，然后是最快的上手方式（首次跑通 ≤3 步）、手动方式作为退路、出问题怎么办（排查表和 FAQ 合成一张）、它不能做什么、卡住了找谁。

**项目架构**：目录和作用，但按「你的数据 / 程序本体 / 改行为的地方」归类，不是模块图。这一节的作用是让人不害怕这个文件夹。

说服、竞品对比、求 star 都不在 README 里，那些是售卖页的活。混进来只会把第一步挤掉。

## 售卖页写成什么样

**为什么需要它**：人群认领（这句话必须能让一部分人主动走开，觉得「好像谁都适合」就是太泛）→ 痛点与解法 → 跟替代方案比成本。

**有什么特色**：每条特色要么解决了前面提过的痛点，要么是那种「作者自己用过才会想到」的细节，要么是强于替代方案的地方。用「你不用再做什么」说，不用参数说。

**掏钱之前**：真实的犹豫（FAQ 写读者真正卡住的问题，不是「问：质量好吗？答：我们用优质材料」）、风险兜底、不适合谁、行动指令。

## 它不会做什么

- 不让你去找素材。README 的报错表从代码里的错误信息字符串抓，前置条件从 CI 配置和 manifest 读。售卖页缺真实痛点时，它会告诉你去客服记录或竞品差评里捞，而不是让你「想几个用户案例」。
- 不默认跑你的项目。只读声明文件和错误字符串就够写出准确的 README。只在声明缺失、且那个信息决定读者会不会卡住时，才跑最小的一条命令（比如 `--version`），并说明为什么要跑。
- 不假设读者懂技术。终端、Python、JSON、环境变量这些词首次出现必须就地解释，命令给 Windows 和 Mac 两套，每段命令上方有一句「这行是干什么的」。
- 不编数字，也不为了「具体」编细节。「用 Excel 记了三次就放弃」这种听着具体但凭空来的说法会被判为幻觉，退回到素材支持的抽象层级。
- 不为了结构整齐凑数。三条特色只有两条有依据，第三条就删掉，不编第三条。依据嵌在句子里，不另开一节列成对账表，那种整齐本身就是 AI 味的来源。
- 不把缺口写进正文。缺了读者也不卡住的整段不写，缺了会卡住的改成读者能自己解决的通用做法，缺的是价格许可证这类承诺信息就留白等你补，然后在回复里列清单。
- 不把维护者数据当卖点。测试通过数、代码行数、覆盖率对非技术读者是噪音。
- 不把两类文案混着写。README 靠承认边界建立信任，售卖页靠给足依据建立信任，方向相反。所以两个 profile 永不同时加载。

## 目录说明（改规则时看）

```
SKILL.md                          流程与铁律，每次加载，故意写短
references/core.md                素材去哪读 + 事实层模板 + 通用质量规则 + persona 自检
references/profile-readme.md      README 的三段结构与规则
references/profile-salespage.md   售卖页的结构与规则
references/humanizer-zh.md        去 AI 痕迹的规则副本，只在你没装 humanizer skill 时才读
references/humanizer-zh.LICENSE.txt  上面那份的 MIT 许可
```

改规则优先改 `core.md` 和两个 profile，别往 `SKILL.md` 加内容。它每次都进上下文，越长模型越容易漏读规则。

`humanizer-zh.md` 是外部项目的副本，别改它，你自己的偏好写进 `core.md`。

## 关于去 AI 痕迹

正文写完的最后一步是整篇去 AI 痕迹，这一步不能省。规则按这个顺序取：

1. 你装了 `humanizer` skill → 调它。规则最细，会跟上游更新
2. 没装 → 读 `references/humanizer-zh.md`，这是同一份规则的随包副本，所以没装也不影响
3. 两个都读不到 → 用 `core.md` 里那张模式表自查，这是最弱的一档

这一步要真的改写。只 grep 一遍破折号个数、数字是 0 就报「通过」，不算跑过。改完它会在回复里说清动了哪几处、哪些地方故意没动（路径、命令、报错原文、故意留作反例的句子都不动）。
